# ADR-034: e2e テストの追加基準と運用ポリシー

## ステータス

Draft

## 関連 ADR

- 依存: ADR-010（dotfiles リグレッションテストの基盤・レイヤー定義）
- 関連: ADR-019（Docker ベース e2e テスト環境）
- 関連: ADR-033（tmux popup リグレッションテスト）

## コンテキスト

ADR-010 で bats-core ベースのリグレッションテスト基盤を導入し、ADR-019 で Docker e2e 環境を構築した。現在 5 つの `.bats` ファイルが稼働しており、新たなバグに遭遇するたびにテストを追加していく運用が想定される。

しかし、すべてのエラーに対して e2e テストを用意するのは非限定的であり、以下の問題がある:

- **テスト維持コスト**: e2e テストは実行環境（Docker + tmux + fish）への依存が大きく、環境変化でテスト自体が壊れるリスクがある
- **CI 実行時間**: Docker build 内でテストが実行されるため、テスト数が増えると CI が遅くなる
- **費用対効果**: 一度きりの設定ミスや typo に対して e2e テストを書いても、再発可能性が低く投資に見合わない

テストを追加すべきケースとそうでないケースの判断基準を明文化し、テスト資産を持続可能に保つ必要がある。

## 設計案

### 案 A: リグレッション駆動テスト（Regression-Driven Testing）ポリシー（採用）

「すべてをテストする」のではなく、**再発リスクの高いバグにのみ e2e テストを追加する**方針を採用する。

#### テスト追加基準（以下のいずれかを満たす場合に追加）

1. **再発実績**: 同じ箇所・同じパターンで 2 回以上バグが発生した
2. **チェーン依存**: 複数コンポーネントにまたがる連携（例: Ghostty CSI → tmux user-keys → bind-key）で、片方の変更が他方を壊すパターン
3. **暗黙の契約**: ドキュメント化されていない前提条件に依存している（例: `$TMUX` 変数のクリア、ソケットパスの形式）
4. **手動検証が困難**: 目視確認では見落としやすい状態遷移やタイミング依存の挙動

#### テストを追加しないケース

- **一度きりの typo・設定ミス**: 修正すれば再発しない単純なミス
- **外部ツールのバグ**: tmux・fish・Ghostty 自体のバグで、アップデートで解消されるもの
- **UI の見た目**: ステータスバーの色・配置など、機能に影響しない表示の問題

#### 運用フロー

1. バグ修正時に上記基準を確認する
2. 基準を満たす場合、修正と同じ PR/コミットでテストを追加する
3. テストファイルは既存の `.bats` ファイルに追加するか、コンポーネント単位で新規作成する
4. テスト追加時は ADR-010 のレイヤー分類（静的解析 / 統合テスト）に従って配置する

### 案 B: カバレッジ目標型（却下）

設定ファイル・関数ごとにカバレッジ目標を設定し、網羅的にテストを追加する方式。dotfiles は通常のソフトウェアプロダクトと異なり、設定の組み合わせが膨大で網羅的テストのコストが高すぎるため却下。

### 変更が必要なファイル

| ファイル | リポジトリ | 変更内容 |
|---|---|---|
| `docs/development.md` | dotfiles | テスト追加基準セクションを追記 |
