# ADR-023: tmux ネスト構成（ローカル+リモート）の採用理由の明文化

## ステータス

Superseded by [ADR-076](076-herdr-migration-from-tmux.md)（`herdr --remote` により tmux ネスト構成と F12 パススルーが不要化）

## 関連 ADR

- [ADR-016](016-dotfiles-remote-profile-support.md) — ネスト構成を前提に F12 パススルー・リモート用テンプレートを設計
- [ADR-021](021-ssh-visual-indicator.md) — ネスト状態の視覚的区別が困難という欠点への対応
- [ADR-022](022-ssh-auto-tmux-attach.md) — リモート tmux への自動アタッチを前提に ssh ラッパーを設計

## コンテキスト

現在、SSH 先での作業は「ローカル tmux の中からリモートの tmux に入るネスト構成」を前提としている。ADR-016（リモート dotfiles セットアップ）、ADR-021（SSH・ネスト状態の視覚的インジケーター）、ADR-022（SSH 時の自動 tmux アタッチ）はすべてこのネスト構成を所与の前提として設計・実装されている。

しかし、「なぜネスト構成を採用するのか」「代替案（ローカル tmux のみで完結する、リモート tmux のみを使う等）と比較してなぜこの構成が優れているのか」という設計判断そのものが ADR として記録されていない。結果として：

1. **設計の根拠が不明**: 後から見たときに「なぜこうなっているのか」が分からない
2. **代替案の検討が不透明**: F12 パススルーの複雑さやキーバインド衝突のコストを払ってまでネスト構成を選んだ理由が残っていない
3. **依存 ADR の前提が宙に浮いている**: ADR-016/021/022 が依拠する前提が暗黙的で、将来の設計判断時に参照できない

## 設計案

### 案 A: ローカル tmux のみ（リモートでは tmux を使わない）（却下）

ローカルで tmux を起動し、SSH 先では素のシェルで作業する。

- **利点**
  - tmux は一層のみでキーバインド衝突・パススルー切替が不要
  - 設定の環境別分離（local/remote テンプレート等）が不要
- **欠点**
  - **リモート側のセッション永続性がない** — SSH 切断でリモートのプロセスが終了する。長時間ビルドや `tail -f` 等を切断後も維持できない
  - リモートで複数ペイン・ウィンドウが使えず、並行作業のたびに SSH を張り直す必要がある
  - `nohup` / `disown` / `screen` 等で部分的に代替できるが、tmux のウィンドウ管理・再アタッチと比べると操作性が大きく劣る

### 案 B: リモート tmux のみ（ローカルでは tmux を使わない）（却下）

ローカルでは Ghostty のタブ・ウィンドウ機能を使い、tmux はリモート側のみで起動する。

- **利点**
  - ネストが発生しないためパススルー切替が不要
  - ローカルでは Ghostty ネイティブの機能（Cmd キー、リンククリック等）をフルに使える
- **欠点**
  - **ローカルのセッション永続性がない** — Ghostty がクラッシュ・再起動するとローカルの全セッションが失われる。ターミナル再起動後に作業状態を復元できない
  - ローカルとリモートで操作体系が異なる（ローカル: Ghostty キーバインド、リモート: tmux prefix キー）
  - ローカルでの Claude Code セッション管理（ADR-003/007/011）が tmux 前提で構築されており、大幅な再設計が必要

### 案 C: ネスト構成（ローカル tmux + リモート tmux）（採用）

ローカル・リモートの両方で tmux を起動し、SSH 時は tmux in tmux のネスト状態になる。tmux の標準的なプラクティスはリモートのみ（案 B）だが、ローカルでも tmux を活用している（Claude Code セッション管理等）ため、ネスト構成が自然に発生する。

- **利点**
  - **双方でセッション永続性を確保** — ローカル側は Ghostty 再起動、リモート側は SSH 切断に耐える
  - ローカル・リモートで同じ操作体系（prefix キー + ペイン/ウィンドウ管理）を使える
  - 各層が独立しており、ローカルのみ・リモートのみの作業にもそのまま対応できる
- **欠点**
  - **キーバインド衝突** — 同じ prefix キーがローカル・リモートで二重に解釈される。これがネスト構成の実質的な課題であり、以下の対応はすべてこの衝突への対策である
    - F12 パススルートグルによるモーダル切替（ADR-016 で対応済み）
    - 視覚的インジケーターによる操作対象の明示（ADR-021 で対応済み）
    - ローカル・リモートで tmux 設定テンプレートの分離管理（ADR-016 で対応済み）
  - **回避手段は確立されている** — F12 パススルー以外にも、prefix キーの分離（ローカル `C-a` / リモート `C-b`）や `send-prefix` 等の一般的な手法がある。致命的な制約ではなく、対応可能なコストと判断した
