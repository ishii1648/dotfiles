# 開発ガイド

## 仕様駆動開発の進め方

実装タスクは以下のサイクルで進める。仕様を完成させてから実装するのではなく、**仕様と実装を行き来しながら育てる**。

### サイクル

1. **受け入れ条件を書く** — 「〜できる」形式で箇条書き（完璧でなくてよい）
2. **実装する**
3. **仕様と実装を同期する** — 実装で判明した変更・追記を受け入れ条件に反映
4. **意思決定があれば ADR を作成する** — `create-adr` スキルを使用（ADR の書き方は `adr-reference` skill を参照）

### ドキュメントの役割分担

| 種類 | 置き場所 | 内容 |
|---|---|---|
| 課題・受け入れ条件 | `docs/issues.md` | 何を解決するか・完了条件 |
| 意思決定 | `docs/adr/` | なぜこう決めたか・却下した選択肢（運用ルールは `adr-reference` skill） |
| 実装 | `configs/` | どう実現するか |
| リファレンス | `docs/reference.md` | コンポーネント・ツール・関数の一覧 |

### ルール

- 受け入れ条件は実装ファイルのそばではなく `docs/issues.md` にまとめる
- 仕様は実装後に更新してよい（後追いOK）
- 「なぜこうしたか」だけ書く。実装手順は仕様に書かない

## 設計検証が必要な場合（Spike パターン）

設計を確定させるために実際に作って確かめる必要があるエッジケース向けのフロー。

### フロー

1. **create-adr** — 受け入れ条件に「Spike: 〜を検証する」と明記し、ADR を作成する
2. **ADR ステータスを `Spike中` に設定** — 通常の Draft と区別する
3. **`spike/NNN-description` ブランチで検証実装** — NNN は ADR 番号
4. **検証結果を ADR に追記** — コンテキストまたは設計案セクションに記録する
5. **ADR ステータスを `Draft` に戻し、設計を確定** — Spike コードは main にマージしない
6. **adr-ship で正式実装** — 通常フローに合流する

### ルール

- `adr-ship` は `Spike中` ステータスの ADR には適用しない
- Spike ブランチのコードは検証完了後に捨てる（main にマージしない）
