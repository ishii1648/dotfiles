# Review ADR

## 概要

ADRファイルのパスを受け取り、3名の専門レビュアーが段階的にレビューを行い（Phase 1: fact-checker → Phase 2: logic-reviewer + consistency-checker 並列）、意見交換を経て最終レビューを `.outputs/claude/` に出力する。

レビューは以下の3観点で行われる：

1. **事実調査レビュー**: コンテキスト（課題）に対して適切に事実調査が行われているか
2. **議論展開レビュー**: 事実調査に基づいて合理的な議論展開がされているか
3. **論理整合性レビュー**: 事実や途中議論と結論に矛盾が生じていないか、結論へたどり着くまでに論理の飛躍がないか

## 引数

- **ADRファイルパス**（必須）: レビュー対象のADRファイルの絶対パスまたは相対パス
  - 例: `docs/adr-api-gateway.md`
  - 例: `.outputs/claude/adr-kubernetes-upgrade.md`

## ワークフロー

### Step 1: 入力の確認

`$ARGUMENTS` からADRファイルパスを取得する。空の場合はユーザーにパスの入力を促す。
ファイルが存在しない場合はエラーを表示して終了する。

### Step 2: ADRファイルの読み込み

対象のADRファイルを Read ツールで読み込み、内容をコンテキストとして保持する。

### Step 3 Phase 1: fact-checker を単独実行（事実確認）

`Task` ツールを1回呼び出して fact-checker のみを実行する。Task は `model: opus` で動作させる。

Task には以下を渡す：
- ADRファイルの全文（読み込んだ内容をプロンプトに含める）
- 担当するレビュー観点と具体的なチェックポイント
- 個別レビューの出力フォーマット（`references/review-criteria.md` 参照）
- 返答は JSON 形式で `{"critical": [...], "major": [...], "minor": [...], "summary": "..."}` とすること

#### Task 1: fact-checker（事実調査レビュアー）

**観点**: コンテキスト（課題）に対して適切に事実調査が行われているか

チェックポイント（詳細は `references/review-criteria.md` 参照）：
- 課題の根拠となる客観的な事実・データが示されているか
- 現状把握が正確で、情報源が信頼できるか
- 調査範囲が課題に対して適切か

### Step 3 Phase 2: logic-reviewer と consistency-checker を並列実行

Phase 1 の fact-checker の結果が出てから、`Task` ツールを2回 **同時に** 呼び出して残り2名のレビュアーを並列起動する。各 Task は `model: opus` で動作させる。

各 Task には以下を渡す：
- ADRファイルの全文（読み込んだ内容をプロンプトに含める）
- **fact-checker の指摘内容（Phase 1 の結果全文）**
- 担当するレビュー観点と具体的なチェックポイント
- 個別レビューの出力フォーマット（`references/review-criteria.md` 参照）
- 返答は JSON 形式で `{"critical": [...], "major": [...], "minor": [...], "summary": "..."}` とすること
- 「fact-checker が指摘した事実問題を前提として評価すること」という指示

#### Task 2: logic-reviewer（議論展開レビュアー）

**観点**: 事実調査に基づいて合理的な議論展開がされているか

チェックポイント（詳細は `references/review-criteria.md` 参照）：
- 評価基準が明示・一貫して適用されているか
- 事実がオプション選定の根拠として使われているか
- 重要な観点（コスト、保守性、リスク等）が網羅されているか

#### Task 3: consistency-checker（論理整合性レビュアー）

**観点**: 事実や途中議論と結論に矛盾が生じていないか、論理の飛躍がないか

チェックポイント（詳細は `references/review-criteria.md` 参照）：
- Context-Decision-Consequencesが整合しているか
- Options Consideredの評価とDecisionの選択理由が一致しているか
- 論理の飛躍がないか

### Step 4: 意見交換ラウンド

Phase 1 と Phase 2 の3つの Task 結果が出揃ったら、各レビュアーの結果を引数として含めた追加の `Task` 呼び出しを3回 **同時に** 実行し、他のメンバーの指摘を踏まえた補足意見を収集する。

各 Task には以下を渡す：
- 自分の観点の初回レビュー結果
- 他の2名の初回レビュー結果（全文）
- 以下の観点で補足意見を返すよう指示：
  - 他メンバーの指摘に同意するか、異なる見解があるか
  - 自分の観点から見て他メンバーの指摘が関連する別の問題を示唆しているか
  - 複数の観点から見て特に重要な問題点はあるか（分類の変更提案を含む）

### Step 5: 最終レビューの統合

チームリーダー（このスキルを実行しているメインセッション）が各メンバーの意見を統合し、最終レビューをまとめる。

レビューの分類基準（詳細は `references/review-criteria.md` 参照）：

| 分類 | 基準 |
|------|------|
| **critical** | ADRの核心的な欠陥。このままでは意思決定として成立しない問題（重大な事実誤認、論理的矛盾、致命的な情報欠落等） |
| **major** | 重要な改善が必要な問題。ADRの信頼性・説得力に大きく影響する（重要な根拠の欠如、評価軸の不整合、論理の飛躍等） |
| **minor** | 軽微な改善提案。ADRの品質向上に役立つが、意思決定の妥当性には大きく影響しない（表現の曖昧さ、補足説明の追加等） |

### Step 6: 結果の出力

`mkdir -p .outputs/claude` を実行後、以下の形式でファイルに出力する：

**ファイル名**: `adr-review-<元ファイル名のベース>.md`

出力フォーマットの詳細仕様は `references/review-criteria.md` の「最終レビューの出力形式」セクションを参照する。サマリーには全体評価と推奨アクション（承認可能 / 軽微な修正後承認 / 要修正 / 差し戻し）を含める。

`[観点]` は `事実調査` / `議論展開` / `論理整合性` のいずれか。

## エラーハンドリング

| シナリオ | 対応 |
|---------|------|
| ファイルが存在しない | エラーを表示してファイルパスの確認を促す |
| ADRの内容が空 | エラーを表示して終了 |
| メンバーからの応答がない | タイムアウトとして残りのメンバーの結果で統合を行う |
