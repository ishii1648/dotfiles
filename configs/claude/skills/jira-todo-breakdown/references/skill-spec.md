# スキル仕様: Jiraチケットからの TODO洗い出し

## スキルが解決すること
Jiraチケットを起点に、関連ドキュメント・コードベースを自動調査し、AI/人それぞれの担当に分けたTODO一覧を生成する。

## 入力
- JiraチケットのURL or キー（例: `SREPO-2071`）

## 共通コンテキスト

t9sチームの技術的意思決定・調査ログは以下のConfluenceに集約されている：

- **t9sトップページ**: https://jira-freee.atlassian.net/wiki/spaces/SPO/pages/2480508411/Tsubermetes+t9s (pageId: `2480508411`)
- **ADR一覧**: https://jira-freee.atlassian.net/wiki/spaces/SPO/pages/2312601820/Architecture+Decision+Records+ADRs (pageId: `2312601820`)

## 指示（プロンプト）

### 1. 情報収集（並列実行）

以下を並列で実行する：

#### 1a. Jiraチケット読み取り
Atlassian MCP経由でチケットのsummary・description（背景・完了条件）を取得。

#### 1b. 関連ADRの自動探索
Jiraチケットのsummary・descriptionからキーワードを抽出し、ADR一覧ページ配下をCQL検索する。

```
CQL: ancestor = 2312601820 AND title ~ "<キーワード1> OR <キーワード2> OR ..."
```

**キーワード抽出ルール**:
- チケットのsummary/descriptionから技術用語を抽出（例: nodepool, istio, karpenter, systems）
- 一般的な単語（「分離」「検討」等）は除外し、固有名詞・技術名のみ使用

ヒットしたADRのうち、チケットの内容と関連性が高いものの本文を取得する。

#### 1c. ADRテンプレートの取得
完了条件にADR作成が含まれる場合、SPOスペースでADRテンプレートを検索する。

```
CQL: space = SPO AND title ~ "ADR テンプレ"
```

最新のテンプレートページの本文を取得し、セクション構成を把握する。

#### 1d. description内のリンク先取得
description内のConfluence・Slack等のリンクを辿り、関連ドキュメントの内容を取得。

#### 1e. コードベース調査
チケットの対象領域に関連するファイル・設定の現状を調査（Explore agentで並列実行）。

#### 1f. 技術スタックの推定
コードベースから実際に使用されている技術を把握し、不採用の技術を推定する。
（例: Karpenter NodePoolが定義されている → EKS Auto Modeは不採用）

### 2. アウトプット生成ルール

#### 構成
以下の順で `.outputs/claude/` に出力する：

1. **背景**: Jiraチケットのdescriptionから簡潔に記載
2. **完了条件**: Jiraチケットから転記
3. **既存設計・関連ドキュメントの要約**: 自動探索で見つけたADR等から命名規則・現行構成を表形式で整理
4. **対象領域の現状**: コードベース調査結果を表形式で整理
5. **AI担当TODO**: Phase別にグルーピング
6. **人担当TODO**: 1つのテーブルに集約、各タスクに「人でなければならない理由」列を付与
7. **実行フロー**: AI→人の受け渡しポイントをASCIIフロー図で可視化

#### AI/人の担当振り分け基準

**AI担当にする（デフォルト）**:
- コードベースの調査・分析
- Datadog MCP経由のメトリクス取得・分析
- kubectl MCP経由のクラスタ状態確認
- ドキュメント（ADR等）のドラフト作成
- コード変更の実装
- helmfile template等による差分検証
- 各環境の検証・レポート作成
- オプションのpros/cons整理

**人担当にする（以下に該当するもののみ）**:
- 技術方針の最終意思決定（AI分析結果のレビュー→承認）
- 組織間の調整・交渉・合意形成
- ADR Driver/Notifiedの記入（起案者・関係者の指定）
- ADRの最終レビュー・承認（公式な意思決定記録のため）

**記載しない（自明なもの）**:
- 環境展開のGo/NoGo判断（PRマージフローに組み込まれており自明）
- PRレビュー・マージ（通常の開発フローであり自明）

#### 表のフォーマット

- AI担当TODOは「#, タスク, 詳細」の3列（担当列は不要）
- 人担当TODOは「#, タスク, 詳細, 理由」の4列
- 人担当の番号体系は `H-1, H-2, ...` とし、AI担当と区別する

### 3. 注意事項

- 既存の設計・ADRがある場合はそれを前提とし、ゼロから検討するタスクにしない
- コードベースから推定した不採用技術は考慮に入れない
- MCP経由で取得可能なデータ（Datadog, kubectl, helmfile等）はAIが取得する前提で設計する
- 「人+AI」のような曖昧な担当は避け、AIが作業→人が承認のように明確に分ける

## Jiraチケットに記載すべき最低限の内容

### 追加指示の原因分析（再評価）

| 追加指示 | 原因 | AI自動探索で解決可能か |
|---------|------|---------------------|
| ADRテンプレはこれ | テンプレートの所在が不明だった | **Yes** - CQL `space = SPO AND title ~ "ADR テンプレ"` でヒット |
| EKS Auto Modeは不採用 | 技術的制約が未記載だった | **Yes** - コードベースにKarpenter NodePool定義がある → EKS Auto Mode不採用と推定可能 |
| NodePool設計ADRを参照して | 既存の設計ドキュメントへの参照がなかった | **Yes** - CQL `ancestor = 2312601820 AND title ~ "NodePool"` で3件ヒット（目的のADR含む） |
| 可能な限りAIでやって | AI/人の担当方針が不明だった | N/A - スキル側のデフォルト動作 |
| セクション分けて | 出力フォーマットの好み | N/A - スキル側のデフォルト |
| 展開判断は自明なので不要 | 粒度の期待値が不明だった | N/A - スキル側のルール |

**結論: 追加指示の原因となった3件はすべてAI自動探索で解決可能。Jiraチケットに追加記載は不要。**

### 必須項目（最小構成）

```markdown
## 背景
何が問題で、なぜこのタスクが必要なのか。

## 完了条件
- [ ] 完了とみなす具体的な条件（成果物・状態）
```

これだけで十分。関連ドキュメント・制約は以下の理由でAIが自動補完する：

| 以前「必須」としていた項目 | 自動補完の方法 |
|------------------------|-------------|
| 関連ドキュメント | ADR一覧(pageId: `2312601820`)配下をキーワードCQL検索 |
| ADRテンプレート | SPOスペース内を `title ~ "ADR テンプレ"` で検索 |
| 制約・前提 | コードベースの技術スタックから推定 + 既存ADRのDecisionセクションから抽出 |

### あると精度が上がるオプション項目

```markdown
## 関連ドキュメント（あれば）
- [特に参照してほしいADR・仕様書へのリンク]

## 制約・前提（あれば）
- AI自動探索では見つけにくい暗黙の制約
```
