# 実装モード ワークフロー

SKILL.md の Step 1 完了後、以下の手順を実行する。

## Step 2: コメントのコンテキスト分析

各ルートコメントについて:

1. `path` フィールドで参照されているファイルを `Read` で読み取り
   - ファイルが存在しない場合はスキップし、サマリーで報告
2. `diff_hunk` で周辺のdiffコンテキストを確認
3. コメント本文からレビュワーの意図を分析:
   - 明示的な修正要求か
   - 質問や確認か
   - 提案（suggestion）か
   - 情報共有・FYIか

## Step 3: トリアージと確認

各コメントを以下の3カテゴリに分類する:

| カテゴリ | 判断基準 | アクション |
|---------|---------|-----------|
| **A: 修正必要** | 明示的な変更要求、バグ指摘、GitHub suggested change | コード修正 |
| **B: 返信のみ** | 意図の誤解、適用不可の提案、設計に関する質問 | 対応なし（返信モードで対応） |
| **C: 対応不要** | LGTM、情報共有、既に別の修正で対応済み | スキップ |

**トリアージ結果をテーブル形式でユーザーに提示し、確認を得てから次のステップへ進む。**

提示フォーマット:

```
| # | ファイル | コメント概要 | カテゴリ | 対応内容 |
|---|---------|------------|---------|---------|
| 1 | src/foo.ts:42 | 変数名を修正すべき | A: 修正 | 変数名を `userId` に変更 |
| 2 | src/bar.ts:10 | なぜこの実装にしたか | B: 返信のみ | （返信モードで対応） |
| 3 | src/baz.ts:5 | LGTM | C: 不要 | スキップ |
```

ユーザーがカテゴリ変更を指示した場合は反映する。

## Step 4: コード修正の実行（カテゴリA）

1. カテゴリAのコメントに対して `Edit` / `Write` で修正を実施
2. GitHub suggested change がある場合はその内容を適用
3. 全ての修正を1コミットにまとめる:
   ```bash
   git add {modified files}
   git commit -m "fix: {変更内容のサマリー（対応したレビューコメントの概要を含める）}"
   ```

**注意:** このモードではコメントへの返信やプッシュは行わない。

## Step 5: サマリー出力と次ステップ分岐

**フルモード（`--response`）の場合**: サマリーを出力後、`workflow-response.md` の Step 2 以降を続けて実行する（返信投稿まで一気に行う）。

**実装モード（args なし）の場合**: 以下のサマリーを出力して終了。

```
## 実装モード 対応サマリー

- 修正済み (カテゴリA): N件
- 返信のみ (カテゴリB): N件 → `--response-only` モードで返信
- スキップ (カテゴリC): N件

### 修正ファイル
- src/foo.ts (変数名修正)
- src/bar.ts (エラーハンドリング追加)

### コミット
- {commit hash}: {commit message}

### 次のステップ
返信を投稿するには `--response-only` 付きで再実行してください。
```
